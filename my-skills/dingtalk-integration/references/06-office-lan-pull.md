# S6 办公网接入：内网如何拉取

形态 B 里，中间件不主动连内网，**是内网主动去取**。这一篇定三件事：用什么方式触发拉取、消费端怎么实现、失败了怎么办。

## 一、触发拉取的方式（你还没定的那个决策）

| 方式 | 实现 | 延迟 | 优点 | 代价 | 适用 |
|---|---|---|---|---|---|
| **① 定时轮询** | 内网常驻小进程/计划任务，每 N 秒 `GET /pull` | N 秒 | 最简单、无长连接要求、任何防火墙都通 | 空转请求多（可忽略）、有固定延迟 | **推荐起步：N=30~60s** |
| **② 长轮询** | `GET /pull?wait=25`，无数据时挂起 25s 再返回 | 秒级 | 延迟低、请求数少 | 中间件要支持挂起（占连接/内存）、nginx 超时要配大 | 想要"准实时"又不想改推送 |
| **③ SSE / WebSocket** | 中间件主动推内网常连 | 亚秒 | 最快 | 要求内网能保持长连接、中间件要管连接生命周期、断了要重连 | 交互式场景（本链路不需要） |
| **④ 钉钉群机器人/邮件通知** | 有数据时发条通知，内网收到再拉 | 分钟级 | 不用常驻进程 | 通知会丢、不可靠、不能当唯一触发 | 只做"提醒有人看" |
| **⑤ 反向：内网起 HTTP 服务让中间件推** | 回到形态 A | — | — | 又要一条入站通路 | **不要**，这是倒退 |

**推荐组合：①定时轮询（30s）作主 + 管理接口 `/stats` 做对账**，需要更低延迟再升级 ②。理由：这条链路是"审批完成后同步数据"，不是聊天，30 秒延迟业务上无感；而长轮询要求中间件与 nginx 都改配置（挂起连接、超时、缓冲），收益不匹配复杂度。

**调度方式**：systemd timer / cron / 常驻 Node 进程（`setInterval` + 指数退避）都可以。**不要**用"用户打开页面时顺便拉"——数据同步不该依赖有人访问。

## 二、消费端契约（照这个写就不会错）

```
loop:
  items = GET /api/pull/<consumer>?limit=50&lease=60
  if items.empty: sleep(30s); continue
  for each item:
      try:
          upsert_local(item.external_id, item.event, item.payload)   # 本地事务，幂等
          acks.push({id: item.id, lease_token: item.lease_token})
      catch err:
          nacks.push({id: item.id, lease_token: item.lease_token, error: str(err)})
  POST /api/ack/<consumer> {acks, nacks}
  if items.has_more: continue   # 立刻再拉一批
  else: sleep(30s)
```

四条铁律：

1. **先落本地事务，再 ack**。ack 之后中间件不再重投；顺序反了会丢数据。
2. **本地 upsert 必须按 `external_id` 幂等**。同一 `external_id` 可能来两次（至少一次投递）。
3. **`event=delete/revoke` 要真的删/作废**，不是忽略。删除操作对"本地没有这条"要视为成功（幂等删除）。
4. **ack 失败不要紧**（租约到期会重投），但本地事务不能重复执行出副作用（如重复发通知）。

## 三、本地落库形态

| 本地表字段 | 说明 |
|---|---|
| `external_id` | 唯一索引，与中间件同一个键 |
| `source` | 哪个 consumer / 哪个审批模板 |
| `payload` | 原始 JSON 留档（排障时可回溯"钉钉当时发了什么"） |
| `business_*` | 解析后的业务字段（按你的系统设计） |
| `synced_at` | 落库时间 |
| `void` | 撤回/作废标记，不物理删除（便于审计） |

**建议留原始 payload**：形态 A 没有落盘，出问题时只能靠钉钉后台翻记录；形态 B 留了原始报文，这是它额外的运维红利。

## 四、失败与顺序

| 情况 | 处置 |
|---|---|
| 单条校验失败（字段缺失/格式错） | `nack` 带错误信息 → 中间件 `attempts+1`，超限转 `dead` → 告警人工处理。**不要**无限 nack 卡住队列 |
| 中间件不可达 | 退避重试（30s → 60s → 120s，上限 5 分钟），别打爆 |
| 内网出口被防火墙拦 | 只放行出站 443 到中间件域名；这点是形态 B 唯一的网络要求 |
| 同一 `external_id` 的 upsert 与 delete 乱序 | 消费端按 `created_at` 排序处理，或按"最终状态"覆盖（delete 优先于 upsert 的旧版本） |
| 大批量涌入（月底集中审批） | `limit` 分批拉，`has_more` 驱动连续拉；中间件侧加限流 |

## 五、监控（最少这五个）

1. `pending` 计数与最老待投递时长（>5 分钟要告警）
2. `leased` 卡住数量（消费方挂了）
3. `dead` 数量（必须人工看）
4. 拉取成功率 / 拉取耗时
5. 内网落库条数 vs 中间件 `delivered` 条数（日对账）

## 六、与形态 A 的差异对照（迁移时看）

| | 形态 A | 形态 B |
|---|---|---|
| 内网要开什么 | 入站 VPN 隧道 + 业务端口 | 只出站 HTTPS |
| 内网要跑什么 | 业务系统本身（被动） | 业务系统 + 拉取器（主动） |
| 谁先知道有新数据 | 中间件（推） | 内网（拉） |
| 断网期间 | 钉钉重试 / 边缘队列 | 中间件堆积，恢复后一次拉完 |
| 排障第一步 | 看 VPN 隧道 `tunnel.up` | 看 `/stats` 的 `pending` |
