# 内网部署:三条入口路径

前提回顾:回调地址是**用户浏览器**访问的,钉钉服务器不访问它 → 整套登录可以完全跑在局域网,
服务端只需出站 `api.dingtalk.com:443`,用户设备需可达 `login.dingtalk.com`(扫码页)。

## 三条路径总览

| | 路径 0:同域名复用 | 路径 A:独立域名+证书 | 路径 B:内网 IP 直连（**默认**） |
|---|---|---|---|
| 适用 | 与已接入系统同域名 | 内网长期演进、多系统、要外网登录 | 单系统、快速接入、只在内网用 |
| 域名/DNS | 不动 | 申请子域名,公网 A 记录 → 内网 IP | 无需域名 |
| 证书 | 不动 | 免费单域名证书(TrustAsia DV 等) | 无(实测形态为纯 HTTP) |
| 钉钉侧 | 不动(端口可自选) | 登记域名(主机匹配) | 登记完整 IP URL(逐字符匹配) |
| HTTPS | 继承 | 有 | **无** |
| 换端口/迁移 | 改 REDIRECT_URI 即可 | 改 REDIRECT_URI 即可 | **必须回钉钉后台改+发布版本** |
| 外网/手机登录 | 视域名解析 | 视解析 | **不可用（只在办公网）** |
| 验证状态 | 实测(端口自选) | 生产完整验证,多人实测 | **本组织实测(2026-11,多人复验)** |

**路径 B 为什么成立**:钉钉只校验 redirect_uri 与登记条目匹配。登记条目本身可以是
`http://<办公网IP>:<端口>/api/auth/dingtalk/callback` 这样的完整 URL(浏览器 302 过去即可达)。
此前"裸 IP 必被拒"的教训实为"IP 与**域名**登记条目匹配不上";直接登记 IP URL 即通过。

**所以:没有外网/移动端登录需求时,默认就用路径 B** —— 少掉域名、DNS、证书三件事,也不会撞上
"回调域名被审批链路占用"的冲突。三条路径的取舍在下面路径 B 小节展开。

## 路径 A 步骤(独立域名 + 公网 DNS 指内网 + HTTPS)

### A-1 域名与 DNS:公网 A 记录直接指向内网 IP

**这是整套方案的核心诀窍,不要用拆 DNS。**

- 域名商/DNSPod 加 A 记录: `<login-domain>` → `<内网源站IP>`(公网 DNS 照实返回私网地址)。
- 为什么不拆 DNS(内网 DNS 单独解析):拆分要求**每台客户端**解析都正确,而现实里
  DHCP 下发公网 DNS、第二台内网 DNS 不同步、代理/加速器自带 DoH、浏览器缓存、虚拟网卡 DNS
  (五个断点,全部实测存在)注定"有的机器行、有的不行",且"过一阵又坏"。
- 公网 A 记录指内网 IP 后,**所有解析通道(系统 DNS / DHCP 公网 DNS / 代理 DoH / 浏览器缓存)
  拿到同一个答案**,问题从根上消失。实测:公共解析器(阿里/腾讯/114/Cloudflare/Google)
  照常返回私网应答,家用路由的 DNS 重绑定保护不拦。
- **必须做 DHCP 保留**:IP 一变,域名解析就断(公网在 DNS 层写死了内网 IP)。

### A-2 证书

- 免费 DV 证书只签发**域名**、不签 IP → 这是路径 A 需要"域名"的硬约束(而非钉钉要求)。
- 单域名免费证书 + 同端口多域名时,服务端按 **SNI** 选证书:主证书 + 额外证书按 SAN 自动登记,
  未匹配回落主证书。验证:
  ```bash
  for n in <域名A> <域名B> unknown.example.com; do
    echo | openssl s_client -connect 127.0.0.1:<port> -servername "$n" 2>/dev/null | openssl x509 -noout -subject
  done
  ```
- 证书到期 = 登录断:配置到期检查(脚本比对剩余天数,<30 天告警/exit 1),**到期前人工盯**。
- CORS:若前后端不同源访问,把登录域名加进 `EXTRA_ORIGINS` 类白名单。

### A-3 服务配置

```
DINGTALK_REDIRECT_URI=https://<login-domain>:<port>/api/auth/dingtalk/callback
```
systemd 场景改 env 后 `daemon-reload` + `restart`。同端口多证书时确认启动日志有
"额外证书(SNI)"加载行。

### A-4 客户端提醒(部署时随网址一起通知)

- 统一用域名访问,**不要用裸 IP**(证书必然名不符,浏览器拦截页会挡住整个 OAuth 跳转);
- 挂代理(Clash 类)的同事:代理按**域名**分流,私网 IP 走直连、域名走远端节点(连不到内网),
  会出现"裸 IP 能开、域名打不开"——在代理规则里给该域名加 **DIRECT**;
  TUN 模式/HTTPS 拦截客户端不读系统绕过列表,要在它自己的规则里放行。

## 路径 B：内网 IP 直连（**无特殊需求时的默认选择**）

> **2026-11 实测（本组织，多人）：钉钉企业内部应用的「重定向 URL」可以直接登记
> `http://<办公网IP>:<端口>/api/auth/dingtalk/callback` 这样的完整内网地址，登录全流程跑通。**
> 代价是**只能在办公网内登录**（手机流量/家里/出差都不行）——对内部工具来说通常正是期望行为。
> 已实测的协议形态只有 `http`；`https` + 内网 IP 未实测（见下方"未实测项"），不要照抄推断。

### 适用与不适用

| 场景 | 是否用路径 B |
|---|---|
| 内部工具、只在办公网用、无外网/移动端登录需求 | ✅ **默认就是它**，配置最省 |
| 全新小系统、不想申请域名/证书、当天要上线 | ✅ |
| 内网数据不出网、任何公网入口都要避免 | ✅（连域名都不需要） |
| 要在钉钉客户端工作台打开（免登/内嵌 webview） | ⚠️ 先实测 http 在你们钉钉版本的 webview 里能否加载 |
| 需要外网/手机登录、或第三方系统对接 | ❌ 换路径 A/C |
| 生产平台且组织强制 TLS（密码登录/管理员权限/API 令牌） | ⚠️ 明文 JWT 风险需组织确认；不接受则走路径 A |

### 步骤（比路径 A 少一半）

1. 钉钉后台 →「重定向 URL」**逐字符**登记完整地址：
   `http://<办公网IP>:<端口>/api/auth/dingtalk/callback`
   （含协议、IP、端口、路径，一个字符都不能差）→ **发布版本**。
2. 服务端 `DINGTALK_REDIRECT_URI` 填**一模一样**的字符串（建议直接复制粘贴，别手敲）。
3. 其余（环境变量、服务端实现、前端脚本）与主流程完全一致——**不需要域名、DNS、证书**。
4. **必做 DHCP 保留**（IP 变了 = 书签断 + 钉钉登记条目失效，双重断）。
5. 验证：办公网内扫码走完一次；日志 `start 302 → callback → exchange 200` 三条齐。

### 为什么它最省（相对路径 A 少做四件事）

| 路径 A 要做 | 路径 B |
|---|---|
| 申请/复用一个子域名 | 不用 |
| 公网 A 记录指向内网 IP | 不用 |
| 签发并安装 TLS 证书 + 到期监控 | 不用 |
| 处理"该域名是否已被审批回调占用"的冲突 | **不存在这个问题**（IP 不可能指向腾讯云边缘） |

最后一条是实际收益：路径 A 最容易翻车的就是域名职责冲突（审批回调占着公网解析 → 登录回调 404），路径 B 从根上没有这个坑。

### 代价（选型时必须说清，别只讲省事）

- **只能办公网登录**：外网、手机流量、家里都会失败（回调地址不可达）。有移动办公需求就别选它。
- **登录态 JWT 走 HTTP 明文**：同网段可嗅探/中间人。内网工具能否接受，按组织安全要求定；不接受就上 TLS（路径 A）或至少限制 VLAN。
- **非 secure context**：`crypto.subtle`、剪贴板 API、Service Worker、摄像头/麦克风、Notification 等 Web API 不可用；浏览器地址栏有"不安全"警告。
- **redirect_uri 逐字符匹配**：换端口、迁机器、加路径都要回钉钉后台改并**重新发布版本**（路径 A 只需改 env）。
- **每个系统一组 `IP:端口` 独立登记**，多系统时管理成本线性涨。
- **DHCP 是命门**：必须做保留；换机/换网段等于重新配置一次钉钉后台。

### 未实测项（别当结论用）

- **`https://<内网IP>:<端口>/...` 能否同样登记通过**：登记层面可能可以（匹配的是字符串），但浏览器会因证书没有 **IP SAN** 而拦页，钉钉内嵌 webview 无"继续访问"出口。若要走这条路，需要 **IP SAN 证书**（多数免费 DV 不签 IP）或内网 CA + 客户端信任自签。**未验证前不要把"https+IP"写进方案。**
- 纯 http 在钉钉客户端内嵌 webview 的兼容性（版本相关，"普通浏览器能开"不能推断"钉钉里能开"）。

**优势小结**：30 分钟级接入、零 DNS/证书、无解析歧义（五断点不存在）、无域名职责冲突。

## 存量系统想改走路径 B:先过三道约束(2026-10-20 本仓库评估实录)

已跑在 HTTPS 上的存量系统想"撤域名、改裸 IP",不是删配置那么简单,逐条检查:

1. **该端口的 TLS 是否被其他链路依赖?** 典型形态:HTTPS 单端口同时承担
   "回源严格校验证书"——反代/边缘 relay 回源只认证书 CN,该端口改成 http 会**当场掐断那条链路**。
   若 HTTPS 是全局开关(单端口 TLS/HTTP 二选一,如 `DISABLE_HTTPS` 环境),不支持双监听时,
   裸 IP 只能**另开附加 http 端口**与 TLS 端口并存(需改代码)。
2. **https + 裸 IP 不可行**:证书没有 IP SAN,浏览器卡证书拦截页,每台设备手动放行、
   钉钉内嵌 webview 无放行出口;实测复现过:TLS alert 46 循环、卡拦截页、OAuth 302 链走不到跳转。
3. **别挪用别的域名**:老域名若被公网职责占用(公网 DNS 指向边缘服务等),内网拿它当登录回调
   = 浏览器解析到公网 → 回调 404;为此恢复拆 DNS = 五断点全部回归。

### 双入口过渡(可回退的迁移法)

钉钉「重定向 URL」支持登记多条,不必一步替换:

```
① 附加 http 端口(现有 TLS 端口与其职责完全不动)
② 钉钉后台追加登记 http://<内网IP>:<新端口>/api/auth/dingtalk/callback + 发布版本
③ REDIRECT_URI 切到 IP 地址,daemon-reload + restart
④ 观察期双入口(IP 主用,原域名回退;DHCP 保留 IP 确认——此时是命门)
⑤ 稳定后再撤域名:DNS 解析、证书、到期监控清单同步更新,通知换地址清书签
```

### 动机审视:省一个域名不是真实收益

公网 DNS 指内网的域名方案已无解析歧义(五断点消失),年维护 ≈ 一张免费证书 + 一条 DNS
记录 + 已有的到期告警。改裸 IP 省的只有这张证书;付出的是:明文传输(JWT/口令/令牌可被
同网段抓包)、secure-context 退化、DHCP 保留升级为命门、多系统弹性永久损失。
**生产平台建议保留域名+TLS**(本仓库 2026-10-20 评估后即选择保留,本节即决策记录)。

## 验证(与主流程一致)

`/diag` → 完整走一次登录 → 服务端日志三条(`start 302 / callback / exchange 200`)→
二次登录复用账号。路径 A 额外看证书:`openssl s_client -servername` 两个域名各就各位;
路径 B 额外确认:服务端真以 HTTP 起了(若框架强制 HTTPS/重定向,回调会断)。

## 排障(内网特有)

- "时灵时不灵 / nslookup 对但浏览器打不开 / 无痕正常普通不正常 / 回调落到 404":
  在**出问题的那台机器**跑 `scripts/client-dns-check.ps1 -Domain <域名> -OriginIp <源站IP>`
  (参数化通用版,路径 A 场景;路径 B 无 DNS 问题,重点查代理与证书拦截页)。
- 日志出现 `[TLS-ERROR] ... alert number 46`:客户端拒绝了源站证书。看 `sni=`:
  空 = 裸 IP 访问(必然);有域名但报错 = 该域名不在证书覆盖内(拼错/没装对应证书)。
- 同一台机器"打不开"、别人都正常:先看源站日志该 IP 有没有到过——没有 = 客户端侧断
  (DNS/代理/证书),源站无从谈起;有 200 = 源站正常,查客户端缓存/扩展/旧书签。
