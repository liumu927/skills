# 合规闸门：形态 B 能不能上

> **这份文件不做结论。** 合规结论必须由数据归属部门 + 信息安全/保密办（涉个人信息还要法务）书面确认，任何人（包括 Agent）不能替代。本文做的是：把"能不能落盘"拆成五个可回答的问题、给出三种结论各自的工程预案，让判定能在一次评审会上结掉，而不是拖到迁移做完了才被否。

## 一、为什么这是个闸门而不是细节

形态 A 与 B 在**数据位置**上是性质差异，不是程度差异：

| | 形态 A（转发） | 形态 B（落盘） |
|---|---|---|
| 业务数据在哪 | 只在办公网 <host> 的库里 | **公网腾讯云服务器上（至少到被拉走为止）** |
| 谁能接触到 | 内网人员 | 加：云厂商运维、你的运维、快照/备份、监控日志 |
| 数据留存 | 由业务库决定 | 由中间件的保留期决定（默认 30–90 天） |
| 泄露后果 | 边界被破才发生 | 单台云主机被拿下即发生 |

所以"B 更优雅"是工程判断；**能不能落地是合规判断**，后者优先。

## 二、五个必答问题（带去评审会）

| # | 问题 | 为什么问 | 答案影响 |
|---|---|---|---|
| Q1 | 这批数据的**分级**是什么（公开/内部/秘密/机密）？ | 秘密级以上基本不允许落公网 | 见判定表 |
| Q2 | 是否含**个人信息**？是否含**敏感个人信息**（身份证/银行卡/生物识别/健康/行踪）？ | 个保法对存储位置与最小必要有硬要求 | 触发脱敏或加密方案 |
| Q3 | 是否涉及**工作秘密/商业秘密**（专利未公开内容、客户名单、报价）？ | 这类数据"出内网"本身就需审批 | 结论 3 风险最高的来源 |
| Q4 | 系统的**等保定级**是多少？云上边界是否已在测评范围？ | 定级对象与边界变了可能要重新测评 | 决定是否要先扩展测评范围 |
| Q5 | **日志、备份、监控**里会不会出现业务字段？ | 最容易漏：payload 进了应用日志等于永久留存 | 强制日志脱敏 |

## 三、判定表（三种结论 → 工程预案）

### 结论 1：允许落盘

条件：数据为内部级、无敏感个人信息（或已通过评估）、Q5 有对策。

→ 按 [05-edge-middleware.md](05-edge-middleware.md) §三原样实施，配套 §3.6 安全清单：静态加密、最小字段、保留期、访问审计。迁移按 [11](11-migration-push-to-pull.md) 全流程走。

### 结论 2：有条件允许（只允许脱敏子集 / 只允许加密后落盘）

两种可选做法，可叠加：

**2a 字段白名单 + 脱敏**

- 落盘前按 schema 白名单只保留必需字段，其余丢弃；
- 手机号/邮箱等做掩码或哈希；姓名可保留（业务要认人）但身份证一律不落；
- 保留期压到最短（如 7 天），`delivered` 当天归档即删。

**2b 字段级加密（推荐给"必须落但云上不能看懂"的场景）**

- 中间件**只存密文**：钉钉侧推送前用内网保管的密钥加密敏感字段（或整包加密），中间件不解密、只做存储转发；
- 密钥只在内网存在（KMS / 环境变量 / 硬件令牌），云服务器上没有任何解密能力；
- 代价：中间件无法做业务级校验（只剩 schema/大小/幂等键），排障只能看信封；
- 这一形态能让"云厂商可接触"降级为"只能看到密文"，是绕过结论 3 的常见正路。

实现要点：`payload_enc`（base64）+ `payload_kid`（密钥版本）；`external_id` 保持明文（幂等键需要）；加密用 AES-GCM，密钥轮换靠 `kid` 双版本并存。

### 结论 3：不允许落盘（涉密 / 敏感个人信息不得出内网）

→ **形态 B 不成立，不要启动迁移**。此时只有两条路：

1. **维持形态 A**（转发），并按 [05](05-edge-middleware.md) §2.4 的 A1–A6 逐条加固：VPN 账号最小化 + 定期审计、relay 不落 body、只读请求也排队、超时与重试参数调优、边缘机器最小化。
2. **形态 A + 单向数据流**：把"查询类"接口从公网摘掉，只保留写入推送；减少暴露面。

> 注意：不存在"中间件只在内存里过一手就不算处理"的说法——只要经过第三方控制的服务器，就属于该第三方的处理环节。别用这种说法去过评审，会被否得更快。

## 四、评审要带的东西（准备清单）

1. 数据流图（照抄 [00-pipeline.md](00-pipeline.md) §一 + [05](05-edge-middleware.md) §3.1，标出"数据在哪些机器上停留、停多久"）；
2. 字段级清单（哪些字段落盘、哪些丢弃、哪些加密）；
3. 保留期与销毁方式（`delivered` 归档 N 天 → 定时删除；备份是否同步删除）；
4. 访问控制清单（谁能登录云主机、谁能调 admin 接口、令牌轮换周期）；
5. 审计与告警（谁拉走、拉走多少、`dead` 是否有告警）；
6. 回退承诺（结论变了能多快退回形态 A —— 见 11 §回退矩阵）。

## 六、一个现实提醒

如果评审结论迟迟不来，不要用"先上 B、以后补手续"的方式推进——B 把数据搬到公网服务器上，事后追认的成本远高于事前评审；而形态 A 已经是合规基线，能扛住这段时间。**A 的加固项（A1–A6）不依赖任何新结论，可以立刻做。**
