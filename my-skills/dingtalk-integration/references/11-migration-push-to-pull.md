# 迁移：透明转发 → 落盘拉取

从形态 A（钉钉 → nginx → relay → OpenVPN → 内网）迁到形态 B（钉钉 → nginx → 落盘 → 内网拉取）。
**目标：钉钉侧尽量少改，内网从"被动接收"变"主动拉取"，最终拆掉 VPN 数据面。**

全程可回退，分六阶段，每阶段独立验收。**不要一次切完。**

## 阶段 0：盘点（半天）

先答清楚，答不上别开工：

| 项 | 要确认的 |
|---|---|
| 现有回调 URL | 钉钉连接器动作里配的是哪几条路径 |
| 幂等键 | 现有 `external_id` 用的是审批实例 ID 吗（不是就先统一） |
| 数据量 | 每天多少条、峰值多少、明细最大行数 |
| 内网出口 | 能否出站 443 到中间件域名（**形态 B 的唯一网络前提**） |
| 合规 | 数据落公网服务器是否被允许（不允许 → 迁移动机不成立，只能加固形态 A）。**先按 [12-compliance-gate.md](12-compliance-gate.md) 出结论并签字** |
| 消费方 | 哪个系统来拉、有没有常驻进程能力、能不能加一张表 |

## 阶段 1：中间件加"落盘 + 拉取"，与转发并存（1–2 天）

- 加 `inbound_message` 表、`/api/inbound`、`/api/pull`、`/api/ack`、`/api/admin/*`（契约见 [05](05-edge-middleware.md) §3.3）。
- **保留原转发路由不动**。此时中间件两种能力都在。
- 用 `curl --resolve` 直接打新接口验证（不碰线上 DNS、不碰钉钉）：

```bash
curl --resolve <域名>:443:<腾讯云IP> https://<域名>/api/inbound/<consumer>/upsert \
  -H "X-API-Token: <边缘令牌>" -H "Content-Type: application/json" \
  -d '{"external_id":"mig-test-001","probe":true}'
# 期望：200 + receipt_id；重复执行 → duplicate:true
```

验收：重复投递不产生第二条；`/stats` 能看到 `pending:1`。

## 阶段 2：内网消费端上线，但**只拉不写业务表**（1 天）

- 内网部署拉取器（见 [06](06-office-lan-pull.md)），落一张**影子表**，不碰生产业务表。
- 定时 30s 拉取 → 写影子表 → ack。
- 验收：`pending` 归零；影子表条数与手工 POST 的次数一致；故意停拉取器 5 分钟，`pending` 涨起来，重启后自动拉完。

## 阶段 3：双通道对比（3–7 天）

- 钉钉侧**同时**配两个动作节点（或连接流里并行）：一个打老转发接口，一个打新落盘接口。
- 每天比对：老链路落库条数 vs 影子表条数 vs 钉钉审批通过数，三者一致。
- 重点看差异：字段缺失、明细行数不符、时间时区、撤回是否都收到。
- **这一步是迁移的安全气囊**：发现差异随时停用新通道，业务无感。

> 代价：双通道期每条数据写两次，中间件与内网多一份负载。控制在两周内。

## 阶段 4：切换主路径（半天，可回退）

- 钉钉侧把动作 URL 从 `/api/<system>/upsert` 换成 `/api/inbound/<consumer>/upsert`；请求体补 `external_id`。
- **改完必须重建连接流**（快照坑，见 [03](03-form-data-out.md)），否则真实触发还走旧地址。
- 内网消费端从影子表切到生产表（同一份消费逻辑，换落库目标）。
- 验收：真发起一单 → 审批通过 → `pending` 出现 → 30s 内进生产表 → `delivered`。
- **回退**：URL 改回老路径 + 重建连接流，5 分钟回退。所以老的转发路由**此时还不能删**。

## 阶段 5：停 VPN 数据面（观察 1–2 周后）

顺序很重要：

1. 确认连续 7 天：`dead=0`、`pending` 最老 < 1 分钟、对账无差异。
2. 停掉 relay 的转发目标（或直接停 VPN 客户端服务），**保留配置与账号**（回退用）。
3. 观察 3 天，确认没有链路再依赖隧道：`journalctl -u openvpn-client@office` 无异常重连、业务无报错。
4. 撤销 VPN 账号 ACL、收掉隧道；`/etc/hosts` 里那条固定解析可以留着（不影响）。

验收：`systemctl status openvpn-client@office` 已停且无业务影响；中间件 `/healthz` 不再探测内网。

## 阶段 6：清理与固化（半天）

- 删除 relay 的转发代码路径与 `spool/` 逻辑（**先打 tag 存档**）。
- 更新文档：拓扑图、令牌清单、告警项、对账脚本。
- 把 `EDGE_TOKENS` / 消费方令牌纳入轮换计划。
- 保留存储：`delivered` 按保留期归档。

## 回退矩阵

| 卡在哪 | 回退动作 | 影响 |
|---|---|---|
| 阶段 1–3 | 什么都不用做（老链路一直在跑） | 无 |
| 阶段 4 切换后 | URL 改回 + 重建连接流 | 5 分钟，可能丢切换窗口内几分钟数据（靠钉钉重试或对账补） |
| 阶段 5 停了 VPN 后 | 重启 VPN 客户端 + relay 转发配置恢复 | 10 分钟 |

**所以 `<system>-relay` 的转发实现与 OpenVPN 配置在阶段 6 之前一律不删。**

## 常见翻车点

| 现象 | 原因 |
|---|---|
| 切换后钉钉还是打老地址 | 连接流快照没重建 |
| 切换后大量 `duplicate:true`、内网没新数据 | 双通道期两条链路用了不同 `external_id` 生成方式 |
| 内网一条都拉不到 | 内网出口没放行 443；或 `consumer` 名拼错（路径与令牌都按 consumer 隔离） |
| 拉到数据但业务表没变 | 消费端只写了影子表；或 ack 在事务提交前发了 |
| `leased` 一直涨 | 消费端进程崩了但租约没到期；等 lease 超时或手动 `replay` |
| 撤回事件没生效 | 只迁了 upsert，忘了把 delete/revoke 也指向新接口 |
