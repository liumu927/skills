# S3 审批数据接出：何时取、怎么触发、发往哪里

这一段回答三个必须定死的问题：**什么时候取**（触发时机）、**用哪个机制取**（触发通道）、**取到什么样**（数据形态）。选错任何一个，后面都要返工。

## 一、触发时机（什么时候取）

| 时机 | 语义 | 能不能拿到完整数据 | 适用 |
|---|---|---|---|
| 审批**通过** | 最后一个节点同意，实例结束成功 | ✅ 完整 | 最常用：入库、发通知、改状态 |
| 审批**结束**（含拒绝/终止） | 成功或失败都算 | ✅ 完整 | 需要"失败也要留痕/撤销"的场景 |
| 审批**撤回** | 发起人撤回已通过的实例 | ✅ 完整 | 必须同步删除/回滚，否则数据悬挂 |
| 审批**进行中**（某中间节点后） | 流程还在走 | ⚠️ 可能被后续节点改变 | 一般不用；预占资源类才用 |

**推荐组合**：通过 → 写入；撤回/终止 → 删除或标记作废。两者都必须带同一个 `external_id`（审批实例 ID），否则会出现"写进去了撤不回来"。

**踩坑**：只在"通过"配了节点、没配撤回，线上就会出现审批撤回后系统里数据还在（本项目实测过）。配的时候一次配齐两条。

## 二、触发机制（用哪个通道取）

四种通道，能力差别很大，别拿轮询当主力：

| 机制 | 配置位置 | 时机精度 | 能做什么 | 硬限制 |
|---|---|---|---|---|
| **① 审批流程内「连接器」HTTP 节点**（当前实现） | OA 审批后台 → 流程设计 → 节点 | 准（流程走到才发） | 直接 POST 到中间件；请求体可绑表单控件值与审批实例 ID | **URL 不支持变量插值**（`${}` 原样发送）；同步等待、超时约 5s；连接流快照坑；失败重试不保证 |
| **② 连接平台「连接流」** | 连接平台 | 准（事件触发） | 循环、分支、多次调用；适合明细逐条处理 | 需要连接流发布；重建才吃新配置；循环内节点都计量 |
| **③ 开放平台事件订阅**（审批实例开始/结束） | 开放平台 → 事件订阅 | 准 | 拿实例 ID 后自己查详情；支持 Stream 模式免公网回调 | 要注册与验签（加密回调）、要维护回调可用性；属于本包未深入覆盖的范围 |
| **④ 定时轮询 OpenAPI** | 自建服务 | 差（取决于间隔） | 兜底对账、补漏 | 有频率限制、延迟、无法感知"刚好通过"；**只做补偿，不做主路径** |

**选型**：
- 数据只是"从钉钉搬到一个能收 HTTP 的地方" → **①**（最简单，钉钉侧零开发）。
- 需要循环/条件/多系统扇出 → **②**。
- 需要事件里的审批元数据（而不只是表单值）、或不想开公网回调 → **③**（Stream 模式）。
- 主路径之外永远配一个 **④ 做对账**：按天拉一遍实例列表，比对中间件里有没有缺（钉钉侧丢事件是真会发生的）。

**①②③ 的共同前提**：得有可被钉钉访问的地址。若目标是内网系统，这个地址只能是公网边缘（见 05）；内网系统本身**不要**要求公网可达。

## 三、取到什么样（数据形态）

### 3.1 表单控件值

- 键 = **字段编码**（`TextField_xxx` / `DDSelectField_xxx` / `InnerContactField_xxx`），不是中文显示名。
- 编码随模板走：删控件重加、复制模板都会变。**每次从"执行详情 → 入参 → 复制 JSON"照抄**，禁止截图 OCR、禁止手抄。
- 值形态按控件类型不同（下拉是 `{label,value}` 对象、联系人是 userId 数组、日期是带假 Z 的字符串），见 08。

### 3.2 明细（子表单/表格控件）

- 明细是一个**数组**，每行是一组字段。
- 连接流里"取审批实例详情"拿到的明细，接口原始返回是 `rowValue` 标签式结构，平台会转成 keyed 对象；**用哪个取决于你走哪个节点**，用之前先在执行详情里看一眼实际形态。

### 3.3 元数据（必带）

| 字段 | 用途 | 注意 |
|---|---|---|
| `external_id` = 审批实例 ID | 幂等键、删除定位 | **必须显式绑定**，不要自己拼 |
| 审批模板/流程标识 | 多模板共用中间件时区分 | 建议一起带上 |
| 审批结果、结束时间 | 判断写入还是删除 | 通过/拒绝/撤回 |
| 发起人 userId | 归属人、通知 | 不是 unionId |

## 四、发往哪里（三种落点）

| 落点 | 路径 | 适合 | 不适合 |
|---|---|---|---|
| **AI 表格** | 连接器直连多维表 API（01/04） | 人要看、要筛选的台账；轻量统计 | 需要事务、复杂校验、对外提供 API |
| **边界中间件** | HTTP 节点 → 公网 nginx → relay（05） | 数据要进内网自有系统 | 中间件被当业务系统用（它只该做安检+暂存） |
| **自建服务直连** | 连接器直连你公网 API | 系统本身就在公网 | 系统在内网（必须过中间件） |

**判断标准**：数据最终要被内网系统消费 → 走中间件；只是留档给人看 → 写 AI 表格；两者都要 → 中间件为主、AI 表格可作镜像（注意两份数据的一致性由你自己保证，别指望钉钉）。

## 五、可靠性设计（这一段决定上线后会不会天天救火）

1. **幂等**：中间件与自有系统都按 `external_id` upsert。钉钉会重试，人也会手动重推。
2. **快速返回**：让钉钉侧拿到 200 的时间尽量短（<2s）。形态 A 是"内网处理完才 200"，慢就超时；形态 B 是"落盘即 200"，天然快。**这是改落盘方案最硬的理由之一。**
3. **不假 200**：中间件不能为了"看着成功"回 200。落盘失败就 5xx/503，让钉钉重试。真实成败必须透传（形态 A 的 relay 也是原样透传，别加缓存篡改）。
4. **可对账**：中间件留接收日志（`external_id` + 时间 + 结果 + 重试次数），否则"到底收到没"永远说不清。
5. **补偿**：主路径之外按天轮询对账（见二·④）。

## 六、验证清单

- [ ] 发起一单 → 审批通过 → 中间件收到 1 条，`external_id` 等于审批实例 ID
- [ ] 同一条数据重复推送 → 中间件/自有系统不产生重复记录
- [ ] 审批**撤回** → 对应数据被删除或标记作废（不是留着）
- [ ] 中间件停掉 → 钉钉侧看到失败（不是静默成功）；恢复后能重放
- [ ] 明细 3 行 → 落地 3 行，不是 1 行、不是 1 格塞数组
- [ ] 表单加了一个新控件 → 编码变了 → 按新编码重新取（旧编码静默为空）
- [ ] 对账：按天拉实例列表，与中间件记录条数一致
