# 公网部署 + 公网域名(路径 C)

> ⚠️ **未实测骨架**:本仓库的实测经验全部来自内网部署(路径 A/B)。本文按标准 OAuth2
> 常规公网部署写,钉钉侧与服务端实现(见 dingtalk-side.md / server-impl.md)与内网完全一致,
> 差异只在基础设施与暴露面。首次按本文落地后,请把实测结论回填进来并删掉本标注。

## 与内网部署的差异总览

| 项 | 内网(路径 A/B) | 公网(路径 C) |
|---|---|---|
| DNS | 公网 A 记录 → 内网 IP(或无域名) | 常规公网 A 记录 → 公网服务器 |
| 证书 | 免费单域名 + 可能 SNI | 常规部署(Let's Encrypt/云证书,可自动续期) |
| 暴露面 | 整系统不出网 | **第一决策:暴露多少** |
| 解析歧义 | 有(需专门设计) | 无(所有通道答案一致) |
| 额外防护 | 基本不需要 | 速率限制/防扫/WAF 按需 |

## C-1 暴露面决策(做之前先定)

1. **整系统公开**:业务页面公网可达。简单,但等于把内网业务系统挂上公网——
   需要评估数据敏感性、加防扫/限速/日志审计。多数办公系统不建议。
2. **只放行登录相关 + 白名单接口**(本仓库边缘方案的反向复用):钉钉 OAuth 只需要
   `GET /start`、`GET /callback` 公网可达(其实只有 callback 必须,`/start` 也可内网发起);
   业务接口走内网或边缘令牌放行。优点:公网攻击面最小;代价:架构多一层。
3. **整系统进内网、仅回调域名公网解析**:如果用户也在内网,这就是路径 A,不用 C。

推荐:除非业务本身要求公网可用,否则不要为了"登录"把整系统暴露——内网场景见 scenario-intranet.md。

## C-2 基础设施

- 域名 + 常规 A 记录 → 公网服务器 IP;HTTPS 用 Let's Encrypt(certbot 自动续期)或云证书。
- 服务器出站可达 `api.dingtalk.com:443`(云上一般无限制,安全组确认)。
- `DINGTALK_REDIRECT_URI=https://<域名>/api/auth/dingtalk/callback`(登记同一条,发布版本)。

## C-3 相对内网新增的防护点(骨架,落地时细化)

- `/callback`、`/exchange`、`/status` 公网可达 → 加基础速率限制(如 express-rate-limit);
  `state`/一次性码本来就有 TTL 与一次性,天然抗重放,保留。
- 反代(nginx/caddy)终结 TLS 时:转发真实 IP(`X-Forwarded-For`)供日志排障
  (日志带客户端 IP 是排障关键,见 troubleshooting.md);
- `Strict-Transport-Security`(HSTS)正常开启;
- 登录成功回跳落点(`DINGTALK_LANDING_URL`)与 CORS 白名单对齐,别把生产回调指到测试域名。

## C-4 验证

与主流程一致(diag → 端到端 → 日志三条 → 二次登录复用账号),另加:
- 公网证书链完整(手机流量/外部网络访问不报证书错);
- 从**办公网外**的网络走一遍登录(排除"只在办公网内通"的隐性问题);
- 速率限制触发行为符合预期。
